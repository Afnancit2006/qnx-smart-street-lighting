# Originality and team-learning checklist

The official brief values code originality and warns against generated or
prebuilt submission code. Treat this workspace as a tutor and engineering
reference, not something to submit without understanding or adaptation.

Before the event, every teammate using a module should be able to:

- Explain why it exists and what happens if it fails
- Draw its queue inputs and outputs
- Explain its scheduling priority relative to the other tasks
- Change one behavior and update the matching test
- Reproduce the essential code from understanding, not copy/paste
- Interpret its test and timing results

During the event:

- Confirm allowed pre-event materials with the assigned mentor
- Write the official solution within the permitted development window
- Use small commits authored by the teammate who did and understands the work
- Keep commit messages factual: `add absolute sensor timer`, not `final code`
- Record design decisions and rejected alternatives
- Cite external documentation and third-party code if any is used
- Do not claim simulator readings are physical sensor measurements
- Do not claim host Linux numbers are QNX real-time measurements

Useful team-owned improvements include a new traffic model, a direction-aware
light wave, a validated QNX native-pulse transport, a BSP-specific hardware
resource manager, original stress tests, or a measured power calibration. One
small well-explained improvement is more credible than a large unexplained code
drop.
